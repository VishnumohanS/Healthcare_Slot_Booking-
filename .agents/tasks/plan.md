# Implementation Plan — Data Flow & Razorpay Integration

## Diagnosis

### Problem 1 — Backend "cannot reach server"
The `.env` file copied from `.env.example` is **missing three required keys**:
`SECRET_KEY`, `RAZORPAY_KEY_ID`, and `RAZORPAY_KEY_SECRET`. The server starts fine
(imports verified), but it must be explicitly launched via `runapplication.bat` or
`python run.py` from `backend/`. The user's error message is generated by the
frontend's `describeError()` in `frontend/src/api/client.js` when no network
response arrives — meaning the FastAPI server is simply not running.

Root cause: user has not run `setupdev.bat` (or ran it but didn't launch
`runapplication.bat`), or ran setup before the `.env` was complete.

### Problem 2 — Doctor never sees patient bookings
The entire booking flow is gated on Razorpay succeeding. Traced end-to-end:

1. `BookingForm.jsx` calls `createPaymentOrder()` → `POST /payments/orders`
2. `payment_service.create_order()` calls `_razorpay_client()` which raises
   `HTTP 503` when `RAZORPAY_KEY_ID` or `RAZORPAY_KEY_SECRET` are empty strings.
3. Because the order creation fails, **no Appointment row is ever inserted**,
   so there is nothing for the doctor to see.

The `list_appointments` service logic for doctors is correct: it filters by
`Appointment.doctor_id == doctor.id` and excludes `payment_pending`, so any
`booked` appointment created after successful Razorpay verification will appear
in the doctor's appointment list. The `AppointmentList` component in
`DoctorDashboard` displays `patient_name` from `AppointmentRead` which is
populated from `patient.name` in `create_order`. This path is sound.

Confirmed in the database: all 5 seed appointments have `patient_id=None`
(inserted by seed SQL, not by the API). Doctors with real `user_id` are IDs 5,
6, 7 (seed doctors 1-4 have `user_id=None`). Once a payment completes, the
appointment is inserted with `patient_id` set and status `booked` — and it will
show on the correct doctor's dashboard immediately.

### Problem 3 — Razorpay checkout modal never opens
Same root cause as Problem 2: `POST /payments/orders` returns 503 before the
frontend can call `loadRazorpay()` or `new window.Razorpay(...)`. The frontend
code in `BookingForm.jsx` is fully implemented and correct — no frontend changes
are needed for the Razorpay flow itself.

### Additional bug found
`backend/app/services/payment_service.py` line 125 calls `hmac.new(...)`.
Python's `hmac` module **does** export `hmac.new` (verified), so this is not
broken. No change needed.

### What is NOT broken (verified)
- Backend import chain — `from app.main import app` succeeds cleanly.
- CORS configuration — frontend origins are in `cors_origins`.
- `AppointmentRead` schema includes `patient_name` — doctor can see who booked.
- `list_appointments` doctor-side filter — correct, excludes `payment_pending`.
- `BookingForm.jsx` Razorpay integration — complete and correct.
- `DoctorDashboard.jsx` → `AppointmentList` data path — uses `appointments` prop
  passed from `App.jsx`'s `listAppointments()` call, which returns doctor-scoped
  rows. The component renders `patient_name` in the "Patient / slot" column.
- `requirements.txt` — `razorpay==1.4.2` is already listed and installed in
  `.venv`.
- `.env.example` — already contains `RAZORPAY_KEY_ID=` and
  `RAZORPAY_KEY_SECRET=` placeholders.

## What needs to change

### Fix A — Add missing keys to `.env`
The live `.env` file is missing `SECRET_KEY`, `RAZORPAY_KEY_ID`, and
`RAZORPAY_KEY_SECRET`. They must be added so the backend can start securely and
Razorpay calls can succeed.

### Fix B — Expose `VITE_RAZORPAY_KEY_ID` to the frontend (optional safety net)
The backend already returns `key_id` in the `PaymentOrderRead` response and
`BookingForm.jsx` correctly reads it from `order.key_id`. No env var is needed
on the frontend. No change required.

### Fix C — Expose `patient_id` in `AppointmentRead` for the doctor dashboard
Currently `AppointmentRead` does not include `patient_id`. The doctor's
appointment list shows `patient_name`, which is sufficient for display. However,
the doctor has no way to distinguish two patients with the same name. Add
`patient_id` to `AppointmentRead` as a nullable int so the doctor's view can
show a unique patient identifier if needed.

**Decision:** Include this — it is a pure schema addition, no DB change, no
migration, and strictly backwards-compatible since it's a new optional field.

  _log = _logging.getLogger(__name__)

              "Payment endpoints will return 503 until both keys are added to .env."
